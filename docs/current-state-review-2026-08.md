## 1. 执行摘要

当前树在**测试层面健康**(双环境 13/13),但深度审查发现三类实质问题:

1. **安全语义脱节(高)**。`--no-token` 回环运行时**无任何 CSRF 保护**(Origin 检查只在 cookie 模式运行)——恶意网页即可对 `http://localhost` 上的运行时执行任意命令(v1-csrf-tokenless,高);`?token=` 查询参数在所有路由可用且**静默禁用 cookie 模式的 CSRF 检查**(v1-token-query-csrf-bypass,中)。TLS 侧:`HCC_RUNTIME_URL=https` 覆盖路径会让所有 CLI 调用失败且 `hcc down` 谎报已停止(TLS-1,高);`hcc web` 不带 `--tls` 重跑会**静默停掉 TLS 运行时降级为明文**(TLS-2,高)。
2. **共享运行时可被无限挂起(高)**。`runTmux` 用无超时 `spawnSync`(xx-02,高)——卡死的 tmux 冻结整个运行时事件循环;请求热路径的注册表文件锁在主线程 `Atomics.wait`(xx-01,中);失败兄弟库迁移无负缓存,每条命令重付 5s 阻塞(xx-05,中)。
3. **v1 时钟安全子系统存在状态机缺陷(高)**。pending-gap 状态机让跨边界基线永久冻结,年龄型 GC 被永久推迟并开出虚假 grace 窗(CS-01,高);宽限期内过期锁行无法清除(CS-04)、ttl<=0 产生永久过期锁(CS-05)、不完整指纹的 peer 永远无法被证据判死(CS-06/v1-legacy)。

## 3. 分领域详细发现

### Committed v1: clock-safety / lock-evidence / optimistic-evidence subsystem

**CS-01(高) `lib/core/coordination/clock-safety.mjs:205` — Pending-gap state machine freezes the boundary-crossing baseline forever, permanently deferring all age-based GC and opening spurious 120s grace windows**
- 机理:Every observation (the reaper ticks every 30s at bin/hcc.mjs:3466, plus every heartbeat/acquire/GC) calls nextObservationGap, which for a normal tick returns {from: previous, to: current, first: false} (line 200). mergePendingGap (lines 205-214) then merges with the persisted gap using `from: Math.min(...)`, `to: Math.max(...)`, `first: persisted.first || observed.first`. The gap is only cleared when grace is entered (lines 287-289: `if (decision.enterGrace) { ... clearPendingGap(db); } else if (pendingGap) { writePendingGap(db, pendingGap); }`). So once any gap is persisted, `from` (and the `first: true` flag from the very first observation, line 180) never advance, and clockSafetyPreviewState (lines 240-245) computes `decisionPrevious = pendingGap?.first ? undefined : pendingGap?.from ?? previous` — permanently frozen in the past. Every subsequent candidate (any lock that expires after the freeze point) and every gcCutoff (which is always ≈ now − δ, i.e. newer than the freeze) is therefore always 'crossed', so decideClockSafety's gc branch (lines 99-107) returns {enterGrace: true, renewOwners: false} on essentially every GC run, and every unknown-evidence crossing opens a fresh CLOCK_GRACE_SEC window. Empirically confirmed with the committed modules (simulated reaper ticks + auto-GC): steady-state GC runs return {"enterGrace":true,"reason":"gc-cutoff"} every time, and a fresh DB returns reason 'first-observation'.
- 失败场景:A project with any regular hook/event activity runs the auto-GC (startup + every 6h, bin/hcc.mjs:3582-3583). Every run observes gcCutoffs newer than the frozen baseline -> enterGrace -> graceActive (bin/hcc.mjs:7727) -> `deferred_expired_locks = clockObservation.expiredLockCount`, history and buffer pruning skipped (bin/hcc.mjs:7765-7806, 7847-7859). Result: expired lock rows are never deleted, events/tasks/messages older than the retention window are never pruned, .hello-cc/bufs is never pruned, and WAL keeps growing — the exact unbounded growth GC was built to prevent (conc-05). The user-visible symptom of `hcc gc` is `deferred_age_based: true` with zero deletions on every run. Each deferring run also re-opens a 120s grace window during which lock acquisition of any expired lock fails (LOCK_HELD, see CS-04) and stale takeovers fail (TAKEOVER_POLICY). Additionally, the freeze makes every expired lock of a stale-but-live owner permanently 'crossed', so observeClockSafetyInTransaction's renewal (lines 298-305) re-extends those locks on every 30s reaper tick — locks of an alive-but-quiet peer effectively never expire.
- 修复:Consume the gap after each observation: reset the persisted gap so `from` tracks the current observation (e.g., store the gap only as (to, firstConsumed) and set decisionPrevious = previous when the gap's `to` is older than `previous`), or simply drop the pending gap when no jump was observed this tick (only persist it for jump ticks and read it once). Also clear `first` after the first observation that uses it.
- 验证:undefined

**CS-04(中) `lib/web/peer-actions.mjs:273` — During any grace window every expired lock row blocks acquisition regardless of owner evidence, and the row can never be cleared while GC is deferred**
- 机理:The acquire conflict test (lines 273-279): `const conflict = subject.locks.find((row) => row.owner !== peer && locksConflict(row, requested) && ( graceActive || Number(row.expires_at) > t || evidenceByOwner.get(row.owner)?.state === 'live' ));` — the `graceActive` term alone creates a conflict for EVERY conflicting lock row, including rows whose owner evidence is 'dead' (verified process gone). Because CS-01 makes grace windows frequent (every GC run, every unknown-evidence crossing), and because the GC that would delete expired rows is itself deferred by CS-01, there is no path that clears an expired lock row during the window: the reaper only reaps peers (never locks), lock-release requires the owner itself, and acquisition is blocked by exactly the row it would replace.
- 失败场景:A hook peer dies (pid gone -> evidence 'dead'). Its lock expires. The next reaper tick or GC run opens a 120s grace (CS-01). During that window peer B attempts to acquire the resource: the dead owner's expired lock row matches and graceActive is true -> LOCK_HELD, even though the owner is verifiably dead. When the grace lapses, B retries and the row is replaced — but if CS-01 keeps reopening grace (every GC run, or any unknown-evidence crossing of a stale peer), B is repeatedly denied for the resource an expired lock is protecting, indefinitely.
- 修复:Qualify the grace term with the absence of verified-dead evidence: conflict only when graceActive && evidenceByOwner.get(row.owner)?.state !== 'dead' (dead evidence is independent of wall clock), mirroring the evidence-first design of the rest of the subsystem.
- 验证:undefined

**CS-05(中) `lib/cli-args.mjs:84` — intOpt accepts ttl <= 0, persisting ttl_sec <= 0 and producing expires_at = now + 0 (or past) locks that every renewal path keeps permanently expired**
- 机理:intOpt (lines 84-89) does `Number.parseInt(...)` and only rejects non-finite values — 0 and negatives pass. webPeerLockAcquire uses `const ttl = intOpt(input, 'ttl', defaultLockTtl)` (web-peer-actions.mjs:238) and inserts `expires_at = t + ttl, ttl_sec = ttl` (line 303); webPeerHeartbeat uses `ttlOverride = input.ttl === undefined ? null : intOpt(input, 'ttl', defaultLockTtl)` (line 126) and writes `expires_at = t + ttlOverride, ttl_sec = ttlOverride` (lines 160-161). With ttl=0 the lock is born expired (expires_at = now), and ttl_sec = 0/negative is persisted. The schema migration only backfills invalid ttl_sec at migration time (schema.mjs:365-375); runtime-inserted values are untouched. All later renewal arithmetic then yields now+0 or now+negative: heartbeat `? + ttl_sec` (web-peer-actions.mjs:164), hook renewal `? + MIN(ttl_sec, 3600)` (bin/hcc.mjs:6407/6412), clock-safety renewal `MAX(expires_at, ? + ttl_sec)` (clock-safety.mjs:301).
- 失败场景:A web client sends ttl:0 (or a negative value, or 1e30 -> parseInt overflow truncation) on lock-acquire. The acquire response reports the lock held 'until <now>'; the lock is immediately expired, provides no protection once the owner's evidence is not live, and its renewal never extends it — while the owner believes it holds the lock. A heartbeat with ttl:0 actively kills the peer's own locks (expires_at = now, ttl_sec = 0), which then cannot be renewed by the hook path either.
- 修复:Reject ttl values that are not positive safe integers in intOpt (or at the acquire/heartbeat call sites with a dedicated positiveIntOpt, as already used for 'stale-after' and 'count' at web-peer-actions.mjs:190/216), and clamp/backfill ttl_sec at write time rather than only at migration.
- 验证:undefined

**CS-06(中) `lib/core/peers/evidence.mjs:16` — Peers whose stored process fingerprint is incomplete are permanently 'unknown' evidence and can never be reaped or have their locks released by evidence**
- 机理:processState (lines 15-23) first does `compareProcessIdentity(evidence.storedIdentity, evidence.storedIdentity) !== 'live'` — a self-comparison that returns 'unknown' whenever the STORED identity is incomplete (compareProcessIdentity, identity.mjs:155-160, requires pid > 0, a non-empty startToken, and a 64-hex commandHash). ### Committed v1: schema v7 migration + DB backups + GC/registry/buffer changes

**v1-02(中) `lib/db/migration-backup.mjs:110` — Migration backups are never rotated, pruned, or restorable, and accumulate a full DB copy on every failed/racing migration attempt**
- 机理:`ensureMigrationBackup` publishes a full `VACUUM INTO` copy as `<db>.pre-v<from>-to-v<to>.<ts>.<suffix>.bak` (20-22, 102-130) and `connect()` runs it as `beforeMigration` on every connection while `readSchemaVersion < 7` (bin/hcc.mjs:777-778). The backup is created *before* the migration transaction; if the migration then fails (crash between backup and tx commit, disk full mid-tx, busy), the DB stays at v6 and every subsequent CLI invocation or runtime request re-runs `beforeMigration` → another full copy. The fanout `migrateRegisteredProjectDbs` (bin/hcc.mjs:792-831) does the same for every registered project DB. Nothing anywhere deletes `.bak` files (grep for `.bak`/`migration-backup` in production code finds only the creation path), and there is no restore command or documented procedure. There is also no disk-space check before `VACUUM INTO`, which transiently needs ~2x the DB size in the staging directory (104).
- 失败场景:A project DB at v6 with a migration that repeatedly fails (e.g., a row that trips the unique-index creation, or the process killed mid-migration). Every `hcc status`/`hcc peer` invocation (each is a fresh process) creates another full `.bak` (potentially hundreds of MB each) before failing, so disk usage grows without bound and the project becomes unusable (fail-closed: `connect()` throws, all commands fail) until the backups are manually discovered and deleted. Even in the healthy case, two racing processes (CLI + runtime) each publish a backup of every unmigrated DB, doubling disk usage per version bump, permanently.
- 修复:Prune/rotate: keep at most N (e.g., 3) backups per project per from/to range, delete older ones after a successful migration, and add a documented restore path (e.g., `hcc db restore <bak>` that checks quick_check + schema version before swap). Check free space before VACUUM INTO and fail with a clear message.

**v1-04(中) `lib/shared/file-lock.mjs:677` — Web runtime event loop freezes up to 5s on a contended registry write: withFileLock waits with Atomics.wait on the main thread**
- 机理:`withFileLock` is a synchronous, blocking lock: `acquire` (629-681) loops `sleep(Math.min(retryMs, remaining))` where `sleep` is `Atomics.wait(waitBuffer, 0, 0, milliseconds)` (19-21) — this parks the entire Node process main thread, not just the calling code. The web runtime's HTTP handler for `POST /api/projects` calls `rememberProject` → `registerProject` → `withFileLock(registryPath, ...)` with the default `timeoutMs = 5000` (bin/hcc.mjs:5369; lib/runtime/projects.mjs:292-296, 275-290). Any concurrent holder of the registry lock (another CLI `registerProject`/`registerProjectActivity` process doing `readProjectRegistry` normalization — stat + realpathSync per project, slow on network filesystems — or a momentarily stale claim) makes the runtime stall for the remaining lock wait.
- 失败场景:A user clicks 'Register Project' in the web UI while a CLI process (e.g., a `hcc run` hook or a slow `hcc register` on an NFS home) holds the registry lock. The single-threaded runtime freezes for up to 5 seconds: all PTY session I/O, tmux polling, WebSocket broadcasts, and heartbeat writes stop, then resume. Under repeated contention every API call that touches the registry incurs this stall; with a wedged-but-live holder the runtime is hard-stalled for the full 5s on each request.
- 修复:Use a nonblocking fast path for the runtime's HTTP handler (as `registerProjectActivity` already does with `nonblocking: true`), or move registry writes off the request path (queue + periodic flush), or implement the lock wait asynchronously (worker/child process) so the event loop is never parked.

**v1-03(低) `lib/db/schema.mjs:119` — Backup created under a race is mislabeled: a process that observes a stale pre-migration version can back up the already-migrated DB as 'pre-v<from>-to-v<to>'**

B's `runSchemaMigrations` then short-circuits, so no error is ever raised.
- 失败场景:CLI runs `hcc register`/any command while the web runtime is handling a request, both racing the v6→v7 migration on the same mesh.db. - 修复:Inside `beforeMigration`, re-read the schema version immediately before `VACUUM INTO` and skip/abort if it changed (or take the backup inside the migration transaction itself with `BEGIN IMMEDIATE` so the version cannot change between backup and migration).

**v1-05(低) `lib/runtime/projects.mjs:316` — registerProjectActivity silently drops registry refreshes on lock contention, and the wall-clock throttle can suppress refreshes for the full duration of a clock step-back**
- 机理:`registerProjectActivity` calls `updateProjectRegistry(candidate, { nonblocking: true })` (316) inside a bare `try { ... } catch {}` (317): if the registry lock is held by another process at that instant, `acquire` throws `ERR_FILE_LOCK_BUSY` immediately (file-lock.mjs:647) and the update is dropped with no retry. The in-process throttle `recentActivityLocks` (302-315) then records the attempt, so an identical refresh within 60s is skipped even if the lock is free — the lost write is never retried by that process. Separately, the persistence throttle compares wall-clock values: `registryTimestamp() - (row.last_seen_at || 0) < REGISTRY_WRITE_THROTTLE_SEC` (282-284); after a backward clock step of D seconds, `now - last_seen_at` is negative for D seconds, suppressing every refresh for that window — the same class of clock-jump hazard the project mitigates everywhere else (CLOCK_GRACE_SEC).
